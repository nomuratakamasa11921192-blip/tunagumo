## 修正した3件

### 1. Webチャットのレート制限が偽装ヘッダで回避できた（最も重要）

`src/api/routes/chat.py` は訪問者のIPを `X-Forwarded-For` の**先頭**から読んでいた。
X-Forwarded-Forは訪問者がブラウザから自由に付けられるヘッダで、Caddyはそれを消さずに
実際の接続元IPを**末尾に足す**。そのため `X-Forwarded-For: 9.9.9.9` と名乗るだけで
「1分5件・1時間30件」の制限を毎回すり抜けられ、値を変え続ければ無制限に回避できた。

末尾を読むよう修正した。末尾なら、ヘッダを足す構成でも上書きする構成でも、
必ず目の前のCaddyが入れた実際の接続元になる。

影響範囲: 公開Webチャット（埋め込みウィジェット）。AI利用料の無駄遣いにつながるが、
テナントごとの日次コスト上限（$2）が残っていたため、被害額の上限自体は保たれていた。

### 2. Stripe Webhookが署名キーのローテーション中に正当な配信を落とす

`Stripe-Signature` ヘッダを `dict()` で解釈していたため、ローテーション中にStripeが
並べて送る複数の `v1` のうち**最後の1つ**しか検証していなかった。新旧どちらかの鍵で
署名された正当な配信を「署名が一致しません」で落とす可能性があった。
全ての `v1` を集め、どれか1つが一致すれば認めるよう修正した。

あわせて、タイムスタンプが数値でないヘッダで `ValueError` → HTTP 500 になっていたのを、
400（形式が不正）で返すよう修正した。

### 3. 画面のCSPを強化（多層防御）

顧客のAPIキーはブラウザのlocalStorageに保存される。従来のCSPは `frame-ancestors 'none'` のみで、
万一どこかに文字列の混入（XSS）があればキーを外部へ送り出せた。次を追加した。

- `connect-src 'self'` … fetch等での外部送信を禁止（キー持ち出し経路を塞ぐ最重要項目）
- `script-src 'self' 'unsafe-inline'` … 外部スクリプトの読み込みを禁止
- `img-src 'self' data: blob:` … 生成画像は同一オリジン配信であることを全箇所で確認済み
- `media-src 'self' https: blob:` … 動画はHiggsfieldのCDNから直接再生するため https: が必要
- `base-uri 'none'` / `form-action 'self'`

締めすぎて表示が消えないよう、画面内の全ての `<img>` `<video>` の配信元を追跡してから決めた。
その根拠を回帰テストにも残してある。

## 問題なしと確認した箇所

- **テナント分離**: 顧客向けルートは例外なく `get_scoped_db`（RLS）。superuser接続は管理画面と、
  設計上テナント横断が必要な2箇所（招待の受諾・Stripe Webhook）のみ。`SET LOCAL` の
  tenant_idは `uuid.UUID()` で正規化してから埋め込んでおり、SQLインジェクションの余地がない。
- **管理画面**: ルーター全体に `require_admin`、キー照合は `secrets.compare_digest`。
- **XSS**: 画面のHTML組み立てを全て追跡し、外部由来の値は例外なく `escapeHtml` 経由だった。
  Markdown風の描画もエスケープ後に変換している。埋め込みウィジェットは `textContent` 描画。
- **SSRF**: 物件URL取込・チラシ画像・メールサーバー接続のいずれも、公開IP確認・接続後の
  再確認・ポート許可リストが実装済み。メールのIMAP/SMTPホストも社内アドレスを拒否する。
- **秘密情報**: Git追跡ファイルと全コミット履歴を走査し、実キーの混入なし。
  ログ方針（プロンプト・成果物本文を出さない）も実装と一致。
- **パスワード**: pbkdf2-sha256 60万回、比較は `compare_digest`。
- **不可逆アクション**: 「先に記録→実行→状態更新」の順序と冪等キー、緊急停止フラグ、
  失敗時は自動リトライせず人間が判断する設計を確認。
- **営業サイト**: 外部スクリプト・フォームなし。`assets/instagram/` が公開されているのは
  Instagram/Buffer側が公開URLから取得する仕様のため、意図どおり。
- **返信先**: 問い合わせへの返信の宛先は必ずDBの記録から取り、リクエスト本文からは取らない。
