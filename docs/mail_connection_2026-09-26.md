# メール接続失敗の調査（2026-09-26、Codex）

## 確認できた原因

- 21:06の画面ではユーザー名・IMAP・SMTP・送信ポートはGmail用の値。保存時の表示は `Failed to fetch`。
- Computer UseのJavaScript接続をリセットして再初期化すると、Chromeのタブ一覧取得と設定画面のボタン操作が復旧した。以前の `Unable to load browser request-header policy` の根本原因や恒久的な解消は未確認。
- Chromeの保存操作をNetwork診断で観測し、`Network.loadingFailed` の `net::ERR_CERT_AUTHORITY_INVALID` を確認。HTTP応答以前のTLS失敗であり、Gmailの認証エラーではない。
- 同じPCの証明書検証でも `app.tunagumo.com` の発行者がFortinetで、信頼チェーンの検証に失敗。比較対象のGoogleとOpenAIへのTLS接続は検証成功。証明書検証の無効化、証明書追加、警告の回避は行っていない。
- VPSのSSHも接続タイムアウト。通信検査機器がどこにあるか、サイトの本来の証明書が現在正常かは、この接続経路だけでは確定できない。接続先をユーザーへ確認中。

## 画面の状態

- 入力済みのパスワードは取得・再表示していない。再読み込みも行わず、未保存の入力を維持した。
- 診断中は「自動返信を有効にする」を画面上でオフにして保存を試したが、TLS段階で失敗。保存完了は確認できていない。実メール送信は行っていない。
- 開いているページはGmailプリセットと件名限定欄がない旧HTML。新規接続時のバックエンド既定値は `[TSUNAGUMO-TEST]` だが、保存後に現行UIで限定範囲を確認するまで自動返信を開始しない。

## 修正と検証

- 共通通信処理でfetch拒否を日本語化。HTTP 502/503/504やJSON以外のエラー応答にも日本語案内を返す。認証・アップロードも同じ処理を使う。
- 応答だけ失われた場合を考慮し、未保存と断定せず、書き込みの自動再送もしない。
- 変更前の画面テスト19件成功。追加した通信切断・HTMLの502応答・不正JSONの3ケースは修正前に失敗し、修正後は画面テスト20件成功。失敗時の入力保持・件名限定保持・ボタン再操作可能・誤った保存成功表示がないことを確認。
- この通信エラー表示修正の本番反映は未実施。直前の本番HTMLは `8c81090e9d6f50fdc2f90697f0bb82dc618554ece63aa1a8d2e3488eee704a15`（当日の反映記録。今回は接続障害のため再取得できていない）。

## 再開時

1. ユーザーの接続先の回答を確認。本人管理の別回線で検証するか、管理ネットワークの場合は管理者へ証明書・接続制限の確認を依頼する。根拠なく証明書を信頼登録したり検査機能を無効化しない。
