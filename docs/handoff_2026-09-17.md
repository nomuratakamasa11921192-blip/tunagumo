## 2. 運用上、踏んではいけない地雷（今回実際に踏んだもの）

1. **`.env`を変えたら `docker compose restart` では反映されない。** 必ず `up -d`。
   restartはコンテナを作り直さないため、古い環境変数のまま起動して本番が502で止まる。
2. **モデル名はAPIのID表記で書く。** 通称 `claude-haiku-4.5` は404になる。
   正: `claude-haiku-4-5-20251001`。`config/*.yaml` の単価表のキーも同じ表記に揃えること
   （ずれると、そのモデルのコストが**0円として記録**され予算管理が狂う）。
3. **APIキーをチャットに貼らない。** 貼った場合は即座に無効化と再発行が必要。
4. 開発用cloneで `docker compose` を使うときは `-p tunagumo-dev`（`SYSTEM_PROMPT.md` §6.1）。

## 4. テストの動かし方

本番と同じDockerで動かすのが基本（PGroongaを含むため）。
```
cd /home/ubuntu/dev/tunagumo/saas/docker
docker compose -p tunagumo-dev --env-file ../.env.test -f docker-compose.yml -f docker-compose.test.yml build api
docker compose -p tunagumo-dev --env-file ../.env.test -f docker-compose.yml -f docker-compose.test.yml run --rm api alembic upgrade head
docker compose -p tunagumo-dev --env-file ../.env.test -f docker-compose.yml -f docker-compose.test.yml run --rm api pytest -v
```
- ソースはイメージに含まれるため、変更後は必ず再ビルドする。テスト前に開発用DBのマイグレーションを適用する（2026-09-17、0020のままだと `inquiry_notify_email` 列不足で失敗することを確認）。
- APIサーバーの常駐は不要。`run --rm` でpytestを直接起動し、ダミーキーで失敗する起動時の実APIヘルスチェックを避ける。テスト検出が0件の場合は成功と扱わない。
- 2026-09-17 Codex再検証で **618件成功・失敗0件・スキップ0件**（開発用Docker、DBは0024まで適用）。業種設定テストの環境変数を `LLM_MODEL` / `LLM_MODEL_LIGHT` に修正済み。
- 開発用cloneの簡易環境（埋め込みPostgres）では、ffmpeg・PGroonga不在により**22件が環境要因で失敗**する。
  この22件は既知で、コードの問題ではない。
- 営業LINEボットのテストは `cd line-bot/test && node bot_test.mjs`。
